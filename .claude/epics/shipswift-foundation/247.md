# Task: downstream-probe 接线与结构

## Description

把 `scripts/downstream-probe`（独立 SwiftPM 包）接上两个新 product，并建立
"每 target 一个 nonisolated 文件"的结构。

⚠️ **本 task 只做接线与结构，不做实质调用点**——见下方 Technical Details。

## Acceptance Criteria

- [ ] `scripts/downstream-probe/Package.swift` 的 `dependencies` / `targets` 接上
      `CoreDesignEffects` 与 `CoreDesignCharts` 两个 product
- [ ] 建立每 target 一个 nonisolated 源文件的结构（可暂为空壳 + 一条注释说明后续由谁填）
- [ ] `cd scripts/downstream-probe && swift build` 绿
- [ ] CI 的 `downstream-probe` job 绿
- [ ] **epic 与本 task 内明写**：实质 nonisolated 调用点归
      `shipswift-effects` 的 A-7（Effects / Charts）与 `shipswift-shaders` 的 B-4（Shaders）

## Technical Details

### 为什么本 task 只能做接线

`scripts/downstream-probe/Package.swift:2-8` 自陈存在理由：

> 下游消费者 probe：从 **nonisolated 上下文**使用 CoreDesign 的公开值类型。
> 存在理由：CoreDesign 的 target 启用了 `defaultIsolation(MainActor.self)`，
> 这会改变公开 API 的隔离契约——而库自身的四条验证命令全都跑在被隔离的
> target *内部*，结构上不可能发现「下游 nonisolated 代码用不了这些类型」。
> **本 probe 是唯一能看见该问题的地方。**

⇒ probe 的价值全在**调用点**，不在 import。但 task 002 交付的是**空骨架 target**
（本 epic 不落任何组件），**没有任何公开值类型可调用**。
⇒ 本 task 强行写调用点只能写出空壳，是自欺。

### 措辞注意（下游 task 会沿用）

实质调用点的验收条件**不要写成"覆盖全部公开值类型"**——那是自指的：
漏写 `public` 的类型压根不算"公开"，probe 自然不覆盖它，FR-5 就没人查。
**按 API 单位清单点名**（Effects/Charts 40 个、Shaders 28 个），
漏 `public` 会在 probe 编译期直接炸出来。
