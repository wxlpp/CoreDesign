# Task: 公约裁决 AD-4——新 target 的登记表作用域

## Description

决定 `CoreDesignEffects` / `CoreDesignCharts` / `CoreDesignShaders` 三个新 target 的
public 类型**归哪套公约管**，并把裁决写进 `docs/component-contract.md`。

**为什么这是一个 task 而不是一个假设**：PRD 初版曾把"新 target 不进 `component-registry.json`"
当作假设，被评审证伪——公约 **AD-2**（`docs/component-contract.md:1254-1274`）逐字裁定
「登记单位是『有 public 类型的 API 表面』……public 的 `ViewModifier` 类型**照常登记，
判定法同样适用**」，且**未按 target 划作用域**；`SpinningModifier` / `FloatingGlassModifier` /
`TelegramGlassButtonModifier` 三个纯视觉件都在登记表里。而守卫今天扫不到新 target
（`ComponentRegistryGuard.swift:366` 硬编码 `Sources/CoreDesign`）只是**实现层盲区**，
不是公约层许可。⇒ 必须显式裁决，不能默认。

## Technical Details

### 为什么样本不能随便选（第 2 轮评审 I-2）

初版写"取 `RadarChart` 与 Effects 的一个 modifier"，两个都选错了：
- `RadarChart` 属 Charts，而 **P 不算 Charts**；
- Effects 的 modifier 形态是 `internal struct + public extension View`，
  按 AD-2 **明文排除登记** ⇒ 拿一个在 b 路线下**零登记成本**的东西去测 b 的成本。

外推出的 `P × 单价` 同时喂 **AD-4 的裁决**与 **task 006 的 `N_B`**，数错会连累两处。

### 自举环已在设计上打破

PRD 的判据要求 b 侧"实做 2 样本"，而能产样本的 `shipswift-effects` A-6 又依赖本 task
完成。**打破方式**：样本作为本 task 内部的子步骤，在仓外做、产物不进主线
⇒ 本 task 自足，不依赖 task 002 的骨架，也不依赖 Epic A。

### 轻公约（a）的最小内容骨架

1. **继承** J-1（禁未豁免 Bool 参数）与 FR-4 文本参数纪律；
2. **不继承**判定法（步骤 1–4）与扩展点判据（J-2）——理由须逐 target 写明；
3. **新增**两条守卫：`EffectsColorLiteralGuard`、`ChromeTextLiteralGuard`（task 003 建）；
4. **登记形态**按上面拍板的二选一，**且必须配守卫**——作用域钉死后不补守卫，
   就是一块无守卫空白地带，与本 epic 的意图矛盾。

⚠️ **成本量级预估 150–250 行**（对照公约本体 1410 行）+ 两条守卫 + 一条差集守卫。
**本仓从无"另立一份公约"的先例**，且公约本体受 `ComponentContractStructureGuard` 等
机器守护——**可行但绝不轻**，这是本 task 要权衡的真实成本。

### 复用提示

本 task 样本的 **notes 与步骤 2 的业界举证可被 A-6 复用**，省一次返工。
