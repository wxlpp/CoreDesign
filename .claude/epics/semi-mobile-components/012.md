# Task: ProgressIndicator 增强 + spinning modifier

## Description

吸收 Semi Design `Spin` 能力，分两部分交付：

1. **`ProgressIndicator` 增强**——给既有 `Sources/CoreDesign/Components/ProgressIndicator/ProgressIndicator.swift` **新增**带可选文案参数的 init/重载，**原样保留现有 `init()`**（NFR-6 无破坏性：不改现有签名，只加新 init）。
2. **`spinning(_:)` modifier**——新增 `Sources/CoreDesign/Modifier/SpinningModifier.swift`，暴露 `View.spinning(_ isActive: Bool, text: LocalizedStringKey?) -> some View`，为任意内容叠加一层加载遮罩。

**FR-3a 例外（关键，须在实现中显式处理）**：`ProgressIndicator.swift` 包装系统 `ProgressView` 时必须显式写 `.tint(Color.accent)`（既有代码已如此，注释解释了原因：避免 `.tint(_:)` 在多个 `ShapeStyle` 重载间解析到 SwiftUI 自带环境 accent 而非 CoreDesign 的 `Color.accent`）。这是 epic 里 FR-3「强调色走 `.tint`」的**唯一**例外，SC-5 的静态核对（"无字面 `Color.accent`"）对本文件豁免。新增的 init 重载**必须延续**这一写法，不得为了"贴合 FR-3"而改成 `.tint` 环境取色——那样反而会破坏既有重载解析行为。`SpinningModifier.swift` 本身不直接包装 `ProgressView`（它组合调用既有 `ProgressIndicator` 组件），因此**不属于**这条豁免范围，若其中出现任何强调色需求须正常走 `.tint`。

## Technical Details

**FR-3a 静态核对豁免记录**：SC-5（"静态核对：无第 1 层色相硬编码、无字面 `Color.accent`"）明确豁免"包装 `ProgressView` 的文件"，即 `ProgressIndicator.swift`。若仓库存在自动化脚本/CI 步骤扫描 `Color.accent` 字面量，须确认该脚本已排除本文件路径，或在扫描规则/PR 描述中显式记录本次豁免（若脚本尚不支持路径豁免，本任务不负责改脚本，只需在 PR 描述与 `docs/` 中写明，留给 013 或后续任务处理脚本层面的豁免机制）。

**`SpinningModifier` 组合而非重复实现**：遮罩内的 loading 视觉直接调用 `ProgressIndicator(text:)`（本任务第一部分的产出），不在 `SpinningModifier` 里重新拼一个 `ProgressView`——这也是为何它不落入 FR-3a 例外范围：它不直接包装系统 `ProgressView`，而是包装已经处理好 tint 的 `ProgressIndicator` 组件。

**测试重点**（Swift Testing，覆盖受控/格式化逻辑）：
- `ProgressIndicator` 新 init 的文案存储正确性（若文案存储逻辑有 trim/空值判断等，抽成可测的纯函数）
- `SpinningModifier` 的 `isActive` 切换不改变底层内容的布局尺寸（遮罩是 overlay，不应影响内容 frame）——可用 `ImageRenderer` 量两态尺寸相等，仿照 `Tag.swift` 中对命中区扩展的实测记录方式

**不做的事**：不改变 `ProgressIndicator()` 现有 `body` 的 tint 写法（这正是要保留的例外）；不新增独立的 "Spin" 顶层组件类型（epic 架构决定：能用 modifier 达成的做成 modifier，不另立组件）；不碰 `Localizable.strings`（复用既有 `"Loading"` 键）、共享测试 suite、`Previews.swift`、`ComponentData.swift`。
